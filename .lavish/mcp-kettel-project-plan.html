Confirmed implementation stack

Go end-to-end, with Charm’s terminal ecosystem.

The CLI and generated MCP server are Go. FastAPI remains the first source framework: the Go scanner reads Python source statically, then emits a Go HTTP-proxy MCP server using the official Go SDK.

Language

Go

One installable CLI binary, fast scans, and straightforward cross-platform releases.

TUI engine

Bubble Tea v2

Owns terminal state, keyboard events, resizing, loading states, and the scan → select → generate flow.

Components

Bubbles v2

The list supplies fuzzy filtering, pagination, help, spinner, and navigation. A custom delegate renders checkboxes and risk badges.

Styling

Generated runtime

Technical architecture

A narrow pipeline with replaceable scanners.

One normalized candidate shape separates source discovery from terminal selection and code generation. Framework-specific logic stops at the scanner boundary.

Module 1

Discovery

Spec scanners read OpenAPI directly. Adapters statically recognize framework code, starting with FastAPI decorators. Both emit the same candidate model.

Module 2

Candidate model

Stable ID, kind, method, route, name, description, parameters, source span, confidence, risk hints.

Module 3

Terminal selector

Search without losing hidden selection state; keyboard navigation; explicit cancel and confirm.

Module 4

Generator

Render selected tools, configuration, README, and one smoke check into a new output directory.

Generated runtime

Keep application logic where it already lives.

How generation works

The MCP is generated deterministically. AI is not required.

The generator is a template compiler: selected candidates already contain the route and JSON Schema needed to emit MCP tools. The same input and selections always produce the same files.

1

Normalize

Turn an OpenAPI operation or FastAPI route into one validated candidate.

2

Select

Discard every unchecked candidate before any files are rendered.

3

Emit tool

Render one MCP tool definition and HTTP handler per selected candidate.

4

Emit project

Write the server, dependencies, environment example, README, and smoke check.

5

Verify

Parse generated code, start the server, and confirm its MCP tool list.

Deterministic vs LLM-based

Best architecture: deterministic core, optional LLM enrichment.

Recommended core

Deterministic generation

OpenAPI or a framework adapter produces structured candidates. Fixed templates turn those candidates into MCP tool schemas and HTTP handlers.

  • Strengths: repeatable output, offline operation, fast generation, cheap execution, easy testing, no hallucinated routes.
  • Weaknesses: limited by the quality of source types/specs and explicitly supported framework patterns.
  • Best for: executable schemas, request wiring, auth configuration, generated files, regeneration, and validation.
Optional later

LLM-based generation

An LLM reads source/spec context and proposes MCP tools, names, descriptions, classifications, or code.

  • Strengths: understands weak documentation, can rank useful functions, improve descriptions, and suggest higher-level tools.
  • Weaknesses: nondeterministic, slower, costs money, sends code to a provider, requires validation, and can invent incorrect behavior.
  • Best for: suggestions that remain reviewable—not the authoritative executable wiring.
ResponsibilityOwnerWhy
Route/spec discoveryDeterministicIt must reflect code and specifications exactly.
JSON Schema and HTTP request mappingDeterministicIncorrect wiring can call the wrong API or send malformed data.
Go server files, dependencies, configuration, verificationDeterministicGenerated projects must be reproducible and testable.
Tool name and description improvementsOptional LLMSemantic phrasing benefits from context, but the user can review it.
Usefulness ranking and grouping suggestionsOptional LLMThis is judgment rather than protocol correctness.
Final tool selectionHumanThe developer owns the security and product boundary.
Recommendation: ship v1 with zero LLM dependency. Later add a “Review with AI” step that receives normalized candidates and returns schema-validated suggestions. Never let AI silently invent routes, parameters, auth, or executable request wiring.
AI’s later role is editorial, not structural: it may suggest clearer names, descriptions, groupings, or risk labels. Deterministic scanning, schema mapping, HTTP wrappers, project files, and validation remain the source of truth.

Implementation structure

Easy to extend at real seams—without a plugin framework.

The normalized Candidate model is the boundary. Go scanner packages produce candidates, optional enrichers suggest presentation changes, and the deterministic Go generator consumes accepted candidates. None of those layers imports another layer’s implementation.

Extension seam 1

Discovery scanners

Every spec reader or framework adapter implements one small contract: receive a root directory and return validated candidates. Add a scanner file and register it explicitly.

Extension seam 2

Optional enrichment

The base pipeline skips enrichment. A future LLM enricher receives candidates and returns suggestions for names, descriptions, tags, and ranking—never authoritative routes or schemas.

Stable core

Deterministic generator

Consumes the same Candidate model regardless of how it was discovered or reviewed. It has no scanner imports and no AI SDK dependency.

Adding a framework later

  1. Add one scanner module.
  2. Map its routes to Candidate.
  3. Run the shared scanner contract fixture.
  4. Add it to the explicit scanner list.

Selector and generator remain unchanged.

Adding AI later

  1. Add one provider-neutral enricher boundary when the second implementation exists.
  2. Keep provider SDKs inside internal/ai.
  3. Validate structured suggestions.
  4. Require user acceptance before applying them.

Discovery and executable generation remain deterministic.

Deliberate limit: no dynamic plugin discovery, dependency-injection container, or generator interface in v1. Use explicit registration. Introduce another abstraction only when a real second implementation needs it.

Quality gates

Test the seams where generated systems break.

Scanner

Golden fixture

One small FastAPI app covers path/query/body inputs, duplicate names, ignored files, and destructive routes.

Selector

State invariants

Filtering never changes selection; select/clear all have explicit scope; cancel never writes.

Generator

Snapshot + build

Generated files are deterministic, pass gofmt/go test, and contain only selected candidate IDs.

Runtime

MCP smoke test

Start generated server, list tools, call one read route, and verify mapped API errors.

Safety

No project execution

Scanner tests include a module with a failing import side effect and prove it is never imported.

Release

Fresh install

CI installs the CLI, generates from the fixture, and runs the generated smoke test.
